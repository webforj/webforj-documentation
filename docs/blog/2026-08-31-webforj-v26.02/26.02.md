webforJ `26.02` is live! The headline is **craftforJ**, a visual development environment that runs inside your app and brings a coding agent with it, one that writes Java against the app actually running in front of you. Alongside it, this release opens your views to AI hosts with MCP Apps, adds push notifications and a `Card` component, brings search to every list component and section labels to `AppNav`, and makes hotswap the default development loop. See the highlights below, and as always, the [GitHub release overview](https://github.com/webforj/webforj/releases/tag/26.02) has the complete picture.

## craftforJ {#craftforj}
<!-- vale Google.Headings = YES -->

**craftforJ** is a visual development environment that ships with webforJ. It runs inside your app in development mode and gives you a live view of the components your Java code created.

<div class="videos-container">
  <video controls preload="metadata">
    <source src="https://cdn.webforj.com/webforj-documentation/video/craftforJ/intro.mp4" type="video/mp4"/>
  </video>
</div>

Because craftforJ reads your app through webforJ itself, it describes the app in the terms you wrote it in. The tree lists the components your Java code created rather than the markup the browser rendered, the properties are the ones your components declare, and the routes are the ones your router registered, together with the access rules you annotated them with.

Select a component by clicking it in the page, change its properties, and the running app updates immediately. When a change is worth keeping, craftforJ shows it as a diff against the Java file that created it and writes it back to your source. Theming works the same way: adjust the design tokens your app is built from, then save the result into your stylesheet.

Projects created with [startforJ](https://docs.webforj.com/startforj) or from a webforJ [archetype](/docs/building-ui/archetypes/overview) come with craftforJ enabled, so it's there the first time you run them. Press <kbd>Alt</kbd> + <kbd>Shift</kbd> + <kbd>D</kbd> to open it.

### The AI assistant {#the-ai-assistant}

craftforJ includes a full coding agent, and what separates it from an assistant in your editor is where it sits: inside the app that's running in front of you.

<div class="videos-container">
  <video controls preload="metadata">
    <source src="https://cdn.webforj.com/webforj-documentation/video/craftforJ/ai-conversation.mp4" type="video/mp4"/>
  </video>
</div>

The agent isn't limited to the property changes you could make by hand. Describe a problem and it writes the code for it, adding methods, changing logic, and restructuring a view as the task requires.

Every edit it writes is staged rather than written to disk, and every staged edit goes to a real Java compiler before you see it. The agent reads the diagnostics that come back and fixes its own mistakes first, so what reaches your review is code that already compiles against your running app. Applying a change restarts the app, and the agent waits for the restart, reconnects, and picks its plan up where it left off. A task spanning several edits and restarts runs to completion.

You decide up front how much it may do on its own: stop for approval on every action that has an effect, apply its own edits but ask before removing something, or run autonomously.

craftforJ ships no model of its own, so you choose the one that runs it. Add an API key for a supported provider, or point craftforJ at a model running locally to keep everything on your machine. Your key is stored on the machine running your app, and never in browser storage.

:::warning AI can still make mistakes
Working against the running app and compiling its own output makes the agent considerably more accurate than one writing blind. It can still be wrong. Review what it did before you keep it.
:::

:::tip Learn More
See the [craftforJ](/docs/craftforj) documentation for the inspector, writing changes to source, routes, theming, and the assistant.
:::

## MCP Apps {#mcp-apps}
<!-- vale Google.Headings = YES -->

The other half of the AI story in `26.02` points the opposite way. Where craftforJ brings an assistant into your app, **MCP Apps** lets an [MCP](https://modelcontextprotocol.io/)-capable AI app open one of your views inside its own conversation.

<div class="videos-container">
  <video controls preload="metadata">
    <source src="https://cdn.webforj.com/webforj-documentation/video/mcp-apps/webforj-mcp-app.mp4" type="video/mp4"/>
  </video>
</div>

The view stays part of the Java app, using the same components, services, routing, and state it uses in a browser. Add `@McpApp` to a routed view:

```java title="InventoryView.java"
@Route("/inventory")
@McpApp(
    name = "inventory",
    description = "Shows the current inventory for a warehouse.",
    displayMode = McpAppDisplayMode.INLINE)
public class InventoryView extends Composite<FlexLayout> {
  // view implementation
}
```

From there, the person and the AI work the same live UI. The AI can supply input when it opens the view, call actions that change what's on screen, and receive context back from the choices the person makes in it, while the person keeps using the rendered webforJ components directly. The route still works at `/inventory` in a browser.

Spring Boot with Spring AI is the primary path, where the integration discovers marked routes and adds them to Spring AI's MCP server. Apps that don't use Spring Boot can use the standard servlet setup instead.

:::warning Host support varies
MCP Apps is an evolving extension of the MCP specification, so hosts adopt its revisions and security policies at their own pace. Your app declares the origins its view loads from and connects to, and a host that permits them renders the view. Hosts can also apply stricter policies. The opening tool always returns its text content, and the route remains available as a regular browser page. Verify each host you target with the steps in [Testing](/docs/integrations/mcp-apps/testing).
:::

:::tip Learn More
See the [MCP Apps](/docs/integrations/mcp-apps/overview) documentation for Spring Boot and servlet setup, opening input, actions, and testing.
:::

## Push notifications {#push-notifications}

`26.02` adds push notifications, which reach a user when your app isn't open. The browser subscribes once, your app stores the subscription, and the server sends to it whenever an event calls for it.

Push ships as its own module:

```xml title="pom.xml"
<dependency>
  <groupId>com.webforj</groupId>
  <artifactId>webforj-push</artifactId>
</dependency>
```

Subscribing happens in a view, in response to something the user did, and hands back the address of that browser:

```java
Push.getCurrent().subscribe().thenAccept(subscriptions::save);
```

Sending happens on the server, from any thread, so a click listener, a scheduled job, and a request handler all work the same way. With Spring the sender is a bean you inject; without it, `new PushSender()` reads the same configuration.

```java
PushMessage message = PushMessage.create("Order shipped")
    .setBody("Order #42 is on its way")
    .setUrl("/orders/42")
    .build();

sender.send(subscription, message);
```

The builder covers what the notification shows and how the push service treats it: body text, an icon, the page that opens on click, action buttons, a tag that replaces a notification already on screen, urgency, and a time to live for a device that's offline. `send()` returns immediately and completes when the push service accepts the message.

Each deployment signs its notifications with its own key pair, which the build plugin generates:

```bash
mvn webforj:push-keys
```

That prints three properties for your configuration. Push also needs a servlet deployment and a secure origin, so `https` anywhere other than `localhost`.

:::warning Reach varies by platform
On iPhone and iPad, push works only for apps added to the Home Screen on iOS 16.4 or later, and `subscribe()` reports `UNSUPPORTED` in a Safari tab. Safari doesn't render notification action buttons, and Android and iOS WebViews don't display notifications at all.
:::

:::tip Learn More
See the [Push notifications](/docs/advanced/push-notifications) documentation for key generation, storing and restoring subscriptions, message options, failure handling, and a complete example.
:::

## `Card` component {#card-component}

`26.02` adds the `Card` component, a surface for grouping related content and actions into a single item.

A `Card` is assembled from slotted regions, covering a figure, an icon, a title, a caption, header actions, a body, and a footer. A region whose slot holds no content isn't rendered, so a `Card` with a body alone is a framed block of content and nothing more.

```java
Card card = new Card(new Paragraph("Sales climbed across every region."));
card.addToIcon(TablerIcon.create("chart-bar"))
    .addToTitle(new H3("Monthly report"))
    .addToCaption(new Paragraph("July 2026"))
    .addToFooter(new Button("Read more"));
```

<!-- TODO: add a ComponentDemo once the Card docs PR and its verified samples are merged. -->

Beyond the regions, the component covers the presentation choices that usually end up as custom CSS. Orientation places the figure over or beside the rest of the card. A shadow scale and a borderless setting combine into the outlined, elevated, and flat treatments most designs reach for. Dividers separate dense regions, and the expanse setting drives padding, gaps, and the size of the title and caption for tighter dashboard tiles. The whole surface accepts a click listener, which makes a card a single navigation target.

:::tip Learn More
See the [`Card`](/docs/components/card) documentation for regions, orientation, elevation, dividers, and click handling.
:::

## Search in every list {#search-in-every-list}

`AppNav` picked up search in `26.01`. In `26.02` it reaches the list components: `ChoiceBox`, `ComboBox`, and `ListBox` all gain an embedded search field that filters items by their text.

The field is off by default. Reach the configuration with `getSearch()`, then turn the field on:

```java
ComboBox comboBox = new ComboBox("Fruit");
comboBox.insert("Apple", "Banana", "Cherry", "Apricot", "Pineapple");

comboBox.getSearch()
    .setFieldVisible(true)
    .setPlaceholder("Search fruits")
    .setEmptyMessage("No fruits found");
```

<!-- TODO: add a ComponentDemo once the search API docs PR and its verified sample are merged. -->

Filtering only hides the items that don't match, so item indexes and the current selection continue to refer to the full list. You can also filter from code with `setTerm()`, which works whether or not the field is visible, so a list can be filtered from your own search UI elsewhere on the page.

:::tip Learn More
See the [Lists](/docs/components/lists/overview#searching) documentation for the field settings and filtering from code.
:::

## `AppNav` section labels {#appnav-section-labels}

`AppNav` also gains `AppNavLabel`, a non-interactive heading that titles a run of items. A label applies to every item following it, up to the next label or the end of the menu, so a long list of top-level items reads as a few named groups without nesting any of them.

Labels go in with `add()` rather than `addItem()`, and the order of the calls defines the sections:

```java
AppNav nav = new AppNav();
nav.addItem(new AppNavItem("Dashboard", DashboardView.class));

nav.add(new AppNavLabel("Analytics", TablerIcon.create("chart-pie")));
nav.addItem(new AppNavItem("Overview", OverviewView.class));
nav.addItem(new AppNavItem("Reports", ReportsView.class));

nav.add(new AppNavLabel("Account", TablerIcon.create("user-cog")));
nav.addItem(new AppNavItem("Profile", ProfileView.class));
```

A label takes the same prefix and suffix components an item does. It also knows when it has nothing left to title: the nav hides a label automatically once its section has no visible items, so it disappears when a search filters them all out, or when they've all been pinned to the top of the menu.

## Hotswap {#hotswap}

The development loop gets faster in `26.02`. A hotswap tool applies compiled class changes straight to the running app without a restart, and the app keeps its state. The affected part of the page rebuilds instead of the browser reloading everything.

Hotswap is configured out of the box in every `26.02` archetype. It's named in the [webforJ build plugin](/docs/configuration/build-plugin) rather than declared as a project dependency, and the run command stays the same:

```xml title="pom.xml"
<plugin>
  <groupId>com.webforj</groupId>
  <artifactId>webforj-maven-plugin</artifactId>
  <extensions>true</extensions>
  <configuration>
    <hotswap>
      <hotswapAgent/>
    </hotswap>
  </configuration>
</plugin>
```

Two tools are supported. **HotswapAgent** is open source, and the build plugin downloads it on the first run and caches it. **JRebel** is a commercial product that you install and license yourself, and the build reads the path you configure and attaches it unchanged.

How much reaches the running app without a restart depends on your runtime. Method body edits apply on any Java virtual machine. Changing the structure of a class, such as adding a field or a method, needs a virtual machine that accepts the `-XX:+AllowEnhancedClassRedefinition` option, which the [JetBrains Runtime](https://github.com/JetBrains/JetBrainsRuntime/releases) provides and the build detects automatically. Without it, method body edits still apply live, and a structural change waits for the next restart, with a warning in the build log and a notice in the browser.

Nothing is deprecated here. [Spring DevTools](/docs/configuration/deploy-reload/spring-devtools) and the [Jetty Maven plugin](/docs/configuration/deploy-reload/maven-jetty-plugin) work exactly as they did before. Hotswap is the new default, and the only one of the three that skips the restart entirely.

:::tip Learn More
See the [Hotswap](/docs/configuration/deploy-reload/hotswap) documentation for configuration, command line selection, and how each kind of change applies.
:::

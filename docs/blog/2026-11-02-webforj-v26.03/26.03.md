webforJ `26.03` is live! The headline is **TestBed**, a browserless way to run webforJ views and components inside plain JUnit tests, no browser and no server in the loop. Alongside it, craftforJ picks up component deletion and system-wide undo and redo, **BBjShip** brings webforJ deployment to BBjServices for BBj developers, Spring Security tightens up across routing and login, and a handful of smaller polish lands on top. See the highlights below, and as always, the [GitHub release overview](https://github.com/webforj/webforj/releases/tag/26.03) has the complete picture.

## TestBed {#testbed}

Testing a webforJ view usually means starting the app, opening a browser and driving it with Selenium or Playwright. That catches what only a browser shows, but every test pays for the browser, the server, and the waiting in between.

**TestBed** is webforJ's new browserless testing. A view runs inside a plain JUnit test. No browser is opened and no server is started. The test adds the view, acts on it the way a user does, and checks the result from Java. Components attach, fire their events, and navigate exactly as they do in a running app, and every interaction finishes before the next line of the test runs, so nothing waits and nothing flakes.

A test reads like the steps a user would take:

```java
@Test
void shouldSubscribeTheEmailTheUserTyped(WebforjTestbed context) {
  context.add(new NewsletterForm());

  var email = ComponentLocator.of(TextField.class).byLabel("Email").locate();
  var subscribe = ComponentLocator.of(Button.class).byText("Subscribe").locate();

  email.setValue("hello@example.com");
  subscribe.click();

  var status = ComponentLocator.of(Paragraph.class).locate();
  assertThat(status.getText()).isEqualTo("Subscribed hello@example.com");
}
```

Component locators, user-shaped interactions, Java assertions, all without a running server. Browser-dependent tests still have their place, but the TestBed is where the fast feedback lives.

For unit tests covering the demo apps in this release, see the [verified sample tests on GitHub](https://github.com/webforj/webforj-samples).

## Delete components from craftforJ {#delete-components-from-craftforj}

craftforJ landed in `26.02` and let you select a component in your running app, change its properties, and write the result back to your Java source. `26.03` extends that pattern to deletion. Select a component in the inspector, delete it, and craftforJ removes the component from the Java file that created it, keeping the source and the running app in step.

Trees of components work the same way as individual ones, so removing a wrapping layout drops the layout and the children it held in one action.

## Undo and redo, including AI edits {#undo-and-redo-including-ai-edits}

craftforJ also gains undo and redo for every action it takes against your running app, including the ones its AI assistant takes on your behalf. Change a button's theme by hand, apply a round of agent edits, delete a layout — every step is reversible, and the undo reaches back into the Java file too. The source and the running app move together, forward or backward, so a change you want to walk back is one keystroke rather than a careful hand-edit of the file the tool wrote.

The practical effect is that experimenting in craftforJ is cheap. Try an edit, run it, undo it if you don't like what you see, redo it if you change your mind. The commit to source is still yours when you want it, and now the commit back out is too.

## BBjShip (for BBj developers) {#bbjship-for-bbj-developers}

This section is directly for BBj developers. If BBj isn't part of your stack, skip ahead — the rest of the release still applies to you.

**BBjShip** is a new BBj plugin that deploys webforJ apps to BBjServices. You build and deploy your app with the webforJ Maven plugin, either on the BBj machine or from another machine such as a CI server, and the app runs in BBjServices like any other app you manage in Enterprise Manager. BBjShip replaces the webforJ install plugin, which is now deprecated and will be removed in a future release.

A deployment passes through three parts:

1. **webforJ build plugin** packages your app with its dependencies and uploads it to BBjShip
2. **BBjShip** installs the app in BBjServices and publishes it under `/webapp/<publish name>`
3. **BBjServices** runs the app, which you manage in Enterprise Manager like any other app

During development, the same build plugin runs your app from your project in the BBjServices on your own machine. Changes you compile reach the running app without a redeploy, and the open pages update automatically.

## Security hardening {#security-hardening}

`26.03` ships a handful of fixes in the authentication and authorization paths that are worth calling out. None of them require a change to your code, but each one closes a gap that could have surfaced in a hardened production setup. If you're running a `26.x` app with Spring Security or BBjShip, this release is worth the upgrade on these alone.

- **CSRF token in Spring Security login and logout forms** ([#1689](https://github.com/webforj/webforj/pull/1689)). The framework-generated login and logout forms now carry the CSRF token Spring Security expects, so the standard protection applies to those forms by default.
- **Route access evaluated before the route is instantiated** ([#1643](https://github.com/webforj/webforj/pull/1643)). Access annotations like `@RolesAllowed` are now checked at the navigation interceptor, so a protected view's constructor never runs for an unauthorized user. See [Securing webforJ routes](/blog/route-security) for the full picture of why this matters.
- **Anonymous Spring Security user treated as unauthenticated** ([#1687](https://github.com/webforj/webforj/pull/1687)). The anonymous principal Spring uses to represent "no login" is no longer counted as a signed-in user, so authentication checks resolve the way you'd expect.
- **BBjShip refuses requests without admin permission** ([#1686](https://github.com/webforj/webforj/pull/1686)) and **BBjShip refuses credentials over plain HTTP from another machine** ([#1688](https://github.com/webforj/webforj/pull/1688)). Two tightenings on the BBjShip side that keep deployment credentials off the wire in cleartext and keep the deployment surface restricted to admins.

Nothing breaks on upgrade. If you're on `26.x` already, the upgrade is a version bump; if you're on `25.x`, see the [automated migration guide](/docs/upgrading/automated-upgrades) for the OpenRewrite recipes that take care of most of the work.

## Smaller improvements worth knowing about {#smaller-improvements-worth-knowing-about}

A few quality-of-life landings alongside the headline features:

- **`HasTheme` and `HasExpanse`** are now implemented wherever components offer them ([#1665](https://github.com/webforj/webforj/pull/1665)), so you can set theme and expanse from code against a uniform API rather than hunting for the right subclass method.
- **Route-granular rebuild in dev** ([#1614](https://github.com/webforj/webforj/pull/1614)). When you change a class used by a single route, only that route rebuilds. Faster feedback loop in bigger apps.
- **Control id on any component** ([#1607](https://github.com/webforj/webforj/pull/1607)). The DOM `id` attribute is now settable from Java on every component, which simplifies CSS targeting and third-party integrations that look up elements by id.
- **Configure router history through the app accessor** ([#1617](https://github.com/webforj/webforj/pull/1617)). The router's history mode is now reachable from `App` rather than needing a separate configuration step.

The full list of fixes is in the [GitHub release](https://github.com/webforj/webforj/releases/tag/26.03).

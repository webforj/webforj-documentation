webforJ `26.03` is live! The headline is [TestBed](/docs/testing/testbed/overview), browserless testing built for the way AI coding assistants work: webforJ views run inside plain JUnit tests with no browser or server involved, so an assistant can check every change right after it makes it. Alongside it, [craftforJ](/docs/craftforj) picks up component deletion and system-wide undo and redo, [BBjShip](/docs/configuration/bbjship/overview) brings webforJ deployment to BBjServices for BBj developers, and a round of security updates lands on top. See the highlights below, and as always, the [GitHub release overview](https://github.com/webforj/webforj/releases/tag/26.03) has the complete picture.

## Browserless testing with TestBed {#testbed}
<!-- vale Google.Headings = YES -->

AI coding assistants now write a growing share of the code in Java apps, and what keeps that code honest is how fast the assistant can check its own work. [TestBed](/docs/testing/testbed/overview) is webforJ's new browserless testing, and it gives assistants that check. A view runs inside a plain JUnit test. No browser is opened and no server is started, so a test finishes inside the JVM and an agent gets a pass or a fail right after every change it makes.

**Snapshots** give the assistant context. A single `matchesSnapshot()` check writes down everything a user would see in a view, one line per component, as plain text stored next to the test. A model reads that file the way it reads code: it gets the exact content of the view without a browser or a screenshot, and when a change breaks something, the failure is a text diff of what moved.

```java
verifyThat(summary).matchesSnapshot();
```

```snapshot title="OrderSummaryTest.shouldMatchTheSnapshot.yml"
# webforJ testbed snapshot v1
- OrderSummary [composite=Div] [node=div]:
  - Paragraph "Order 1042" [composite=Element] [node=p]
  - TextField [label=Note] [placeholder="Delivery instructions"]
  - Paragraph "Discount applied" [composite=Element] [node=p] [hidden]
  - Button "Pay" [theme=primary]:
    - Icon [slot=prefix] [name=credit-card] [composite=Element] [node=dwc-icon]
  - Button "Cancel" [disabled]
```

The [webforJ MCP server](/docs/ai-tooling/mcp) is backed by the TestBed documentation and API reference, so an assistant writes tests against the real API instead of guessing at it.

The same tests work just as well for the developers reviewing that code. A test reads like the steps a user would take:

```java
@Test
void shouldSubscribeTheEmailTheUserTyped(WebforjTestbed context) {
  context.add(new NewsletterForm());

  var email = ComponentLocator.of(TextField.class).byLabel("Email").locate();
  var subscribe = ComponentLocator.of(Button.class).byText("Subscribe").locate();

  email.setValue("hello@example.com");
  subscribe.click();

  var status = ComponentLocator.of(Paragraph.class).locate();
  assertThat(status.getText()).isEqualTo("Subscribed hello@example.com");
}
```

Components attach, fire their events, and navigate exactly as they do in a running app, and every interaction finishes before the next line of the test runs, so nothing waits and nothing flakes. Browser-dependent tests still have their place for what only a browser shows, but TestBed is where the fast feedback lives.

:::tip Resources
- [TestBed documentation](/docs/testing/testbed/overview): setup, locators, user interactions, assertions, and snapshots.
- [TestBed unit tests for the documentation demos](https://github.com/webforj/webforj-documentation/tree/main/src/test/java/com/webforj/samples/unit): every demo in the webforJ documentation is covered by TestBed tests, a working reference you can browse.
:::

## craftforJ: delete components, undo and redo {#craftforj}

[craftforJ](/docs/craftforj) landed in `26.02` and let you select a component in your running app, change its properties, and write the result back to your Java source. `26.03` extends that same pattern to deleting components, and makes every change craftforJ makes reversible.

  <video controls preload="metadata">
    <source src="https://cdn.webforj.com/webforj-documentation/video/craftforJ/delete-components.mp4#t=0.5" type="video/mp4"/>
  </video>
</div>

Select a component in the inspector and delete it. craftforJ removes the component from the Java file that created it, so the source stays in step with the running app. Trees of components work the same way as individual ones, so removing a wrapping layout drops the layout and the children it held in one action.

Every one of those actions can now be undone and redone, including the ones the AI assistant takes on your behalf. Change a button's theme by hand, apply a round of agent edits, delete a layout: every step is reversible, and the undo reaches back into the Java file too. The source and the running app move together, forward or backward, so a change you want to walk back is one keystroke rather than a careful hand-edit of the file the tool wrote.

The practical effect is that experimenting in craftforJ is cheap. Try an edit, run it, undo it if you don't like what you see, redo it if you change your mind. The commit to source is still yours when you want it, and now the commit back out is too.

:::tip Learn More
See the [craftforJ](/docs/craftforj) documentation for the inspector, source changes, and the assistant.
:::

## BBjShip {#bbjship}

[BBjShip](/docs/configuration/bbjship/overview) brings the webforJ development experience to BBj developers. With BBjShip, `mvn` runs your app straight from the project in the BBjServices of your own machine, with the same dev tools every other webforJ app gets:

- [Live reload](/docs/configuration/deploy-reload/bbjservices): changes you compile reach the running app without a redeploy, and the open pages update on their own.
- [Hotswap](/docs/configuration/deploy-reload/hotswap): HotswapAgent swaps changed classes into the running BBjServices, set up for you on the first run.
- [craftforJ](/docs/craftforj): select a component in the running app, change it, delete it, or ask the AI assistant, and the change lands in your Java source.

When the app is ready, the same build plugin deploys it, either from the BBj machine or from another machine such as a CI server, and the app runs in BBjServices like any other app you manage in Enterprise Manager.

BBjShip also comes with its own [`bbjship` command line](/docs/configuration/bbjship/command-line) for BBj administrators. On the BBj machine, it lists the deployed apps, deploys or undeploys an app, turns the deployment endpoint and development runs on or off, and resets everything BBjShip set up:

```bash
bbjship apps list
bbjship apps undeploy my-app
```

:::warning The webforJ install plugin is deprecated
BBjShip replaces the [webforJ install plugin](/docs/configuration/bbj-installation/configuration). As of `26.03` the install plugin is deprecated, and a future release removes it. If your project deploys with the install plugin today, move it to BBjShip: a single OpenRewrite run updates the `pom.xml` and `webforj.conf`, and your Java code stays unchanged. See [Existing projects](/docs/configuration/bbjship/existing-projects) for the steps.
:::

:::tip Learn More
See the [BBjShip](/docs/configuration/bbjship/overview) documentation for installation, getting started, deployment, existing-project setup, command-line reference, and troubleshooting.
:::

## Security updates {#security-updates}

`26.03` also includes security improvements to authentication and authorization in the Spring Security integration. They don't require any change to your code, and we recommend upgrading to pick them up.

Nothing breaks on upgrade. If you're on `26.x` already, the upgrade is a version bump; if you're on `25.x`, see the [automated migration guide](/docs/upgrading/automated-upgrades) for the OpenRewrite recipes that take care of most of the work.
